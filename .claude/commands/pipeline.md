요청: **$ARGUMENTS**

너는 이 파이프라인의 **오케스트레이터**다. 직접 구현하지 말고 각 단계를 서브에이전트에게 맡긴다.
서브에이전트는 이 대화 맥락을 물려받지 않는다 — 필요한 건 전부 프롬프트와 핸드오프 노트로 넘긴다.

## 0. 준비

- 요청에서 짧은 kebab-case slug을 뽑아 `.claude/handoff/<slug>.md` 를 만든다.
- 첫 줄에 제목, 그 아래 `## 요청` 섹션에 위 요청을 **원문 그대로** 적는다.
- 각 에이전트에게 **이 파일의 절대경로**를 넘기고, 자기 섹션을 덧붙이라고 지시한다.

## 1~4단계

각 단계는 `run_in_background: false` (동기)로 실행한다. 순서:

| 단계 | 에이전트 | 건너뛰는 경우 |
|---|---|---|
| 1 | `spec` | 없음 |
| 2 | `design` | 화면에 보이는 것이 안 바뀌는 작업 (로직·데이터만) |
| 3 | `build` | 없음 |
| 4 | `verify` | 없음 |

**각 단계가 끝나면 결과를 5줄 이내로 요약해 보고하고 거기서 멈춘다.**
사용자가 다음으로 가자고 하기 전에 다음 에이전트를 부르지 않는다. 승인 없이 4단계를 연달아
태우면, 기획이 틀렸을 때 나머지 셋이 통째로 버려진다.

단계별 유의점:
- **1단계 후**: `spec`이 §2 위반을 지적했으면 그걸 **요약 맨 위에** 올린다. 열린 질문이 있으면
  `AskUserQuestion`으로 묻고, 답을 노트에 반영한 뒤 승인을 받는다.
- **3단계 후**: 바뀐 파일 목록과 `git diff --stat`을 함께 보여 준다.
- **4단계 후**: 실패가 있으면 `build`에게 **실패 항목만** 넘겨 되돌린다 → 다시 `verify`.
  **2회까지**. 그래도 안 되면 사용자에게 상황을 그대로 보고하고 멈춘다.

## 마무리

검증이 통과하면:
- 이번에 정한 것 중 **다음 사람이 몰라서 다시 밟을 판단**이 있으면 `CLAUDE.md §10`에
  한 줄로 올릴 것을 제안한다. 문서는 CLAUDE.md 하나다 — 핸드오프 노트는 작업용 임시 파일이다.
- 커밋은 사용자가 요청할 때만 한다.

## 이 명령을 쓰지 않아야 할 때

- 버그 수정 → `build` + `verify` 둘만 돌린다
- 문구·상수 하나 수정 → 파이프라인 없이 그냥 고친다
- "어떻게 되어 있는지" 질문 → 에이전트를 부르지 말고 직접 읽고 답한다

4단계는 **새 기능일 때의 기본값**이지 의무가 아니다.
